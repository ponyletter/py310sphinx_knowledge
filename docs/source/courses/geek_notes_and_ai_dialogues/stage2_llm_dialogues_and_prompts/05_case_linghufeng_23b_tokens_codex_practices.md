## 一、核心洞察：从“对话辅助”到“AI Native”的认知跃迁

在绝大多数开发者还在小心翼翼计算 API 费用、把大模型当成“高级代码补全插件”时，令狐峰在 7 天时间内跑出了 230 亿 Token 的极高强度消耗。

这次极限实战给出的最深刻结论是：**真正拉开生产力代差的，从来不是“会不会写一段精妙的 Prompt”，而是是否具备 AI Native（AI 原生）的心智模型。**

```{mermaid}
flowchart LR
    subgraph 传统辅助模式["❌ 传统低效模式：人盯机器（人是绝对瓶颈）"]
        U1["开发者单句发问"] --> M1["AI 输出单段代码"]
        M1 --> U2["开发者肉眼查验并手动复制"]
        U2 --> M2["遇到报错再手动贴回去"]
    end

    subgraph 原生系统模式["✅ AI Native 闭环模式：AI 自主推进，人做裁判"]
        U3["目标与验收标准 (DoD)"] --> A1["Codex / Agent (Plan 模式拆解)"]
        A1 --> T1["自动化执行与文件修改"]
        T1 --> T2["终端运行测试与 Lint 校验"]
        T2 -->|失败| A1
        T2 -->|通过 (Exit 0)| R1["交付代码 + 变更单 + 测试证据"]
    end
```

### 为什么说“省 Token”是最大的战略陷阱？

1. **机会窗口远贵于算力成本**：
   - 商业世界里最稀缺的资源是**你的注意力、决策精力与产品的市场交付窗口**，而不是几百元、几千元的 Token 费用。
   - 当你为了“省一点 Token”而反复人肉检查、限制 AI 并发、放弃跑测试时，你实际上是在用极其昂贵的人类时间去补贴便宜的算力。
2. **授权的二元法则**：
   - 敢不敢让 AI 连续自主工作几小时甚至几天？如果你不敢，本质上是因为你没有为它设计清晰的**目标**与**验收标准（Acceptance Criteria）**。
   - 真正的 AI Native 开发者思考的是：**“如何尽可能减少我的干预，让系统自动推进并输出确定性结果。”**
3. **烧 Token 的终极产物不是聊天记录，而是系统资产**：
   - 随风消逝的临时 Prompt 没有任何护城河；
   - 必须通过大规模的实践消耗，将高频逻辑固化为 **自动化 Skill、外置规则库（Rules）、测试套件（Test Suite）与失败反例库（Negative Patterns）**。

## 二、【完整收录】50 条烧 Token 和使用 Codex 的方法（含深度工程注解）

以下为令狐峰实战总结的 50 条原则全文收录，并在关键法则下附上工程落地详解：

### 1. 认知与心智模型（原则 1–8）

1. **相信未来是一个普通人靠想法也能暴富的时代，前提是你学会无限烧 token 的方式。**
   - *工程注解*：算力正在成为新的“数字劳动力资本”。过去组织一个 10 人的产研团队需要昂贵的管理成本与招聘周期，现在你可以随时唤醒十几个 Agent 替你打工，关键在于你是否具备指挥大规模算力的系统能力。
2. **真正拉开差距的不是“会不会用 AI”，而是拥有 AI Native 的思维，不要让人成为瓶颈，思考怎么减少自己的参与，你敢不敢让 AI 连续工作几小时、几天，甚至长期替你推进一个目标。**
   - *工程注解*：破除“人肉中继器”思维。凡是需要你反复点“继续”、手动复制控制台报错、手动查验输出的环节，都说明当前工作流存在缺陷。
3. **学会搭建稳定、低成本的模型调用方案。Token 成本降不下来，你就会下意识少思考、少尝试、少并行。**
   - *工程注解*：心理账户效应真实存在。一旦单次调用昂贵，开发者就会本能地陷入“紧缩心智”，不敢开多分支测试、不敢做全库静态扫描。
4. **想办法让账号拥有更充足的 Token 配额。可以研究 OpenCodex、cc switch。**
   - *工程注解*：配置多账号负载均衡与快速轮换工具（如 `cc switch` 或基于反向代理的多 Key 轮询），避免单账号触发 Rate Limit 导致整个研发闭环停滞。
5. **不要把“省 Token”当成最高目标。Token 可以再买，真正稀缺的是你的时间、注意力和机会窗口。**
6. **烧 Token 不是让 AI 陪你闲聊，而是让它持续搜索、分析、执行、验证，最后交付可以直接使用的结果。**
7. **最有价值的不是一个神奇提示词，而是一套能够反复运行、持续优化的工作流程。**
8. **相信 AI，理解 AI，然后尽可能让 AI 去做。很多事情不是 AI 做不了，而是你没有真正把权限和任务交给它。**

### 2. 业务重构与模型选型分层（原则 9–16）

9. **再次强调不要让人成为工作流里的瓶颈。每次需要你复制、粘贴、确认、整理，都应该思考能否继续自动化。**
10. **AI Native 不是“原来的业务加一个聊天框”，而是重新设计整个业务，让 AI 成为默认执行者。**
    - *工程注解*：不要让 AI 去适应传统瀑布流或繁琐的手工流程；从第一天起就以“Agent 能够自行执行 Shell、读写文件、跑测试、打 Git Tag”作为业务基础设施的前提。
11. **不懂一个行业有时反而是优势。你没有被旧规则限制，更容易让 AI 带着你从第一性原理重新拆解行业。**
12. **遇到新行业，不要先花三个月学习。先让 Codex 调研市场、整理术语、分析竞品，再用真实项目反向学习。**
13. **做新业务时，先考虑能不能让 AI 完成，再考虑要不要招人。很多过去需要一个团队的事情，现在可能只需要一个负责人。**
14. **一定要优先使用当前能力最强的模型。模型能力差一点，可能不是结果差一点，而是整个复杂任务根本跑不通。**
    - *工程注解*：顶级推理模型（如 Claude Sonnet 5 / Opus、GPT-5 / o3）与普通轻量模型存在不可逾越的“逻辑相变点”。在复杂架构设计中省几美分，代价是后面花几天时间排查诡异 Bug。
15. **简单任务可以交给便宜模型，关键判断、复杂编码和长期任务交给顶级模型。不要为了省小钱，浪费更多返工时间。**
    - *工程注解*：采用 Pareto 分层架构——用 Flash / Mini 模型做批量数据清洗、初步代码翻译与纯文本格式化；用顶级推理模型做架构拆解、核心算法推演与最终代码审查。
16. **学会观察 Codex 的额度和重置时间。临近重置还有大量额度，就安排代码审计、竞品调研、批量测试等重任务。**

### 3. 目标管理与 Plan 模式工程化（原则 17–25）

17. **不要等到额度快过期才随便烧。提前准备一个“高 Token 任务池”，有剩余额度时直接启动。**
    - *工程实践*：在项目仓库维护一个 `BACKLOG_HIGH_TOKEN.md`，预先准备好“全量测试覆盖率提升至 95%”、“全库重构扫描与坏味道检测”、“50 个对标竞品产品体验分析报告”等后台长程任务，随时填补闲置算力窗口。
18. **学会使用目标模式。把一个需要数小时甚至数天的结果设成目标，让 Codex 围绕最终交付持续推进。**
19. **目标要写结果，不要只写动作。不要说“研究一下竞品”，要说“交付竞品数据库、差异分析和可执行方案”。**
20. **学会使用 Plan 模式。复杂任务先让 Codex 拆步骤、找风险、确定验收标准，再开始执行，返工会少很多。**
    - *实操流程*：在执行任何跨文件重构前，要求 AI：① 列出受影响模块；② 评估破坏性变更风险；③ 输出分步执行清单；④ 等待人工输入 Proceed 确认后再动代码。
21. **简单任务别过度规划，复杂任务别直接开干。判断标准是：做错一次的返工成本高不高。**
22. **给 Codex 明确的完成标准。例如“页面能打开”不够，要写清楚响应速度、移动端效果、异常状态和测试要求。**
23. **不要只告诉 AI“做什么”，还要告诉它“做到什么程度”。没有验收标准，AI 很容易交付一个看起来完成的半成品。**
24. **大任务尽量交付文件、代码、表格或网页，不要只停留在聊天答案。能沉淀的成果，才有复利。**
25. **让 Codex 先读取现有项目、历史文档和真实数据，再提出方案。上下文越真实，输出越少像套话。**

### 4. 自动化验证、连接器与 TDD（原则 26–34）

26. **为长期项目编写 `AGENTS.md`，把项目规则、目录结构、禁区和验收方式写进去，避免每次重新解释。**
    - *工程注解*：项目规则是注入 Agent 潜意识的宪法。一旦规范固定，每次启动会话即可自动加载，无需重复提示。
27. **把经常重复的操作做成 Skill。一次写好规则，以后一句话就能触发完整流程。**
28. **把高频提示词升级为模板，把模板升级为 Skill，再把多个 Skill 串成自动运行的业务系统。**
29. **学会使用工具和连接器。让 Codex 直接读取代码、文档、邮件和数据库，少做人工搬运。**
30. **不要复制几万行日志给 AI。让 Codex 自己搜索关键词、定位异常时间段、提取相关上下文，更快也更准确。**
    - *实操命令*：教 AI 使用 `grep -rn "ERROR" /var/log/app.log | tail -n 50` 或利用正则过滤日志，而不是把整本几百兆日志刷进上下文导致上下文爆炸。
31. **遇到 Bug，不要只让 AI 猜原因。让它复现问题、读取日志、缩小范围、编写测试，最后验证修复。**
32. **修复问题时要求 Codex 先写失败测试，再修改代码。能被测试捕获的 Bug，才更不容易再次出现。**
    - *核心工作法：TDD（测试驱动开发）闭环*：
      ```bash
      # 1. 先写复现 Bug 的测试用例 (此时运行必须报错失败)
      pytest tests/test_issue_123.py  # 状态: FAILED
      # 2. 编写修复业务逻辑代码
      # 3. 再次运行该测试直至通过
      pytest tests/test_issue_123.py  # 状态: PASSED
      # 4. 运行全量测试套件防止产生新回归
      pytest tests/
      ```
33. **不要用“感觉差不多”验收。让 Codex 跑测试、查看页面、检查日志，用证据证明任务已经完成。**
34. **做网页时，让 Codex 同时检查桌面端、移动端、加载状态、空状态和错误状态，别只看首页截图。**

### 5. 多模态、浏览器操作与红蓝对抗（原则 35–42）

35. **学会让 Codex 操作浏览器。大量调研、录入、页面测试和后台操作，本质上都可以转化成浏览器工作流。**
    - *工程基建*：结合 Playwright、Puppeteer 或 Chrome CDP，让 Agent 能够自动打开网页、填表单、抓取动态渲染内容、执行端到端 E2E 测试。
36. **让 AI 看图、看截图、看视频，不要什么都靠文字描述。多模态输入经常比你解释十分钟更准确。**
37. **不要自己逐个整理竞品。让 Codex 批量搜集、分类、去重、打标签，再由你判断真正值得关注的信号。**
38. **相信自己的想法，但前提是看过足够多的竞品、用户反馈和失败案例。自信应该建立在信息密度上。**
39. **一个想法不要只生成一套方案。让 Codex 同时给出保守版、激进版、低成本版和最快验证版，再进行比较。**
40. **学会并行推进。市场研究、产品设计、技术验证和内容生产可以同时运行，不必等上一件事做完。**
41. **并行不是让十个 AI 重复回答同一个问题，而是把任务拆成互不依赖的子问题，最后再汇总判断。**
42. **让最好模型最高的推理审查，执行用中等推理即可。**
    - *推理预算分配策略*：
      - 架构规划与代码审查：开启 Claude 3.7 / Opus Thinking (High Reasoning Budget)；
      - 代码搬运与单测生成：使用中等或常规推理档位（Medium Reasoning），大幅节省耗时并提升生成吞吐。

### 6. 避坑复盘、硬件基建与提效 Skill（原则 43–50）

43. **重要决策不要只问“这个想法好不好”，要让 AI 主动反对你：哪里会失败、什么假设最危险、如何最低成本证伪。**
    - *红蓝对抗 Prompt 模板*：
      > “请扮演我最严苛的竞争对手和技术审查官。针对我刚才提出的架构方案，列出最可能导致项目失败的 5 个致命缺陷、被我忽视的暗含假设，以及如何在 24 小时内以最小成本将其证伪。”
44. **学会洞察 Codex 或 Claude 的周额度的重置时间，是有规律的，不要浪费剩余的 token。**
45. **一次对话只解决一个问题，会浪费 Codex 的连续工作能力。尽量把“调研—方案—实现—测试—复盘”连成闭环。**
46. **每完成一个项目，都让 Codex 复盘：哪些步骤浪费了 Token、哪些信息重复提供、哪些流程可以自动化。**
47. **建立自己的失败案例库。AI 犯过的错误、无效提示词和项目踩坑，都应该沉淀成下一次的约束条件。**
    - *工程规范*：在项目内维护 `ANTI_PATTERNS.md`，把 AI 曾经写错过的正则、用错的异步方法、破坏过的环境变量记录在案，启动时作为负向约束注入。
48. **买一台性能更好的电脑，建议是 1 万以上的 Mac，尤其是需要同时运行 Codex、浏览器、开发环境和部署 Docker 时。生产工具卡顿，会直接限制你的并行能力和思考速度。有段时间，我只能每天烧 30 亿 token，因为电脑成为了瓶颈。**
    - *硬件建议*：高强度并行开发时，多容器 Docker、无头浏览器、本地 LSP 索引与多 Agent 进程极其吞噬内存。推荐 **Apple Silicon (M系列) 32GB 或 64GB+ 统一内存**，避免 Swap 频繁交换导致进程假死。
49. **不要为了烧 Token 而烧 Token。试试装一下这几个 Skill：MarkItDown 插件，将 PDF、Word、PPT 等文件转换为纯净 Markdown 格式，减少无效 Token 消耗，效率提升 50%；安装 Ponytail 技能，自动检测并复用已有代码，减少重复编写，Token 消耗降低 50% 以上。**
    - *核心提效组件*：
      - **MarkItDown**：由微软开源的轻量转换工具，过滤 PDF/Docx 中无意义的二进制与排版噪音，转化为高信息密度的 Markdown，输入 Token 减少 50%~80%；
      - **Ponytail Skill / 代码检测复用机制**：在生成新代码前自动语义扫描现有代码库的公共函数与工具库，严禁 AI 重新发明轮子。
50. **最终的竞争不是谁掌握了更多提示词，而是谁建立了一个能持续消耗算力、自动完成任务、不断积累资产的 AI 生产系统。**

## 三、实操对比：传统开发者 vs AI Native 极客工程流

| 对比维度 | 传统开发者使用 AI | AI Native 极客工程流（令狐峰模式） |
| :--- | :--- | :--- |
| **核心心态** | 计较 Token 花费，怕账单超标，抠抠搜搜 | 抢时间、抢窗口，把 Token 当数字水手无上限投入 |
| **工作方式** | 人在终端前守着，逐句提问，手动复制代码 | 制定清晰目标与验收标准，授权 Agent 异步自主跑通闭环 |
| **排错手段** | 遇到报错肉眼看，手动修改再测试 | 先命令 AI 写失败的自动化测试（TDD），再由测试驱动自愈 |
| **交付标准** | “我觉得代码看起来能跑就行” | 终端 Exit Code 0、测试全部通过、提供真实运行日志与证据 |
| **资产沉淀** | 留在一堆杂乱无章的临时聊天记录里 | 沉淀为可复用的 Skill、工程规范文档与失败案例反例库 |
| **并行能力** | 单线程交互，一个人盯一个对话框 | 多终端、多 Worktree 并行，双模型红蓝对抗审查 |
| **硬件认知** | 认为 AI 都在云端，本地电脑无所谓 | 投资 1 万+ 高配 Mac（32G/64G 内存），防止本地成为算力并行瓶颈 |
| **提效组件** | 盲目复制粘贴长篇文档 | 挂载 MarkItDown 净化输入、Ponytail 复用代码，压榨有效 Token |
