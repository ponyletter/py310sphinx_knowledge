# 【实战复盘】HP：用 Codex 3小时做出优惠券聚合小程序与 5 个踩坑教训

> **案例作者**：HP  
> **项目名称**：【挺会过日子】微信小程序（美团/饿了么等 CPS 优惠券聚合工具）  
> **核心标签**：`小程序开发` `MVP验证` `SPEC方法` `CPS业务` `真机调试` `避坑指南`  
> **实战指标**：3 小时完成可用小程序，首周无公域推广近 300 用户，产生真实返佣订单  
> **关键洞察**：三小时做出小程序不难，难的是把第一版收缩到一个真实、可验证的领券动作。开发速度提升后，产品取舍成为新的瓶颈。首版后台再完整，也不能替代核心需求验证。

---

## 一、为什么要做这个小程序？

### 1.1 业务切入逻辑与立项考量
1. **具备 CPS 变现基础**：此前作者做过 CPS（按销售额分成）业务，深知其收益模式清晰、无库存积压、属于典型的零边际成本管道收入；
2. **身边高频刚需**：身边朋友几乎每天都有点外卖的需求，但经常私信要优惠券链接，每次人工找链接、复制发送极其繁琐低效；
3. **利基市场空间**：市面上大部分小程序只做美团/饿了么外卖券，而除了高频外卖券，像打车、电影票、电商等低频生活优惠券同样存在领取场景。

### 1.2 目标用户画像
- **受众特征**：白领、在校大学生、年轻租房一族；
- **核心痛点**：
  1. 不知道外卖每天都可以先领大额红包再下单；
  2. 不知道除了外卖之外，出行、娱乐也存在平台优惠券；
  3. 想要一个清爽聚合、无需频繁跳转多个群找链接的工具。

### 1.3 核心问题定义与极端克制
许多开发者在立项时，往往陷入“自我感动”：一上来就想做积分商城、签到任务、拼团砍一刀、社交分享、数据分析面板。

作者在立项之初就定下了严格的边界：
> **第一版最核心的问题只有一个**：“用户能不能在 3 秒钟内成功领到券，并在美团/饿了么中下单成功抵扣。”

围绕“优惠券成功领取”作为第一版 MVP（Minimum Viable Product，最小可行性产品）。如果这个核心链路验证不成立，后续所有花哨功能都是徒劳；如果核心链路成立，再根据真实数据推进迭代。

```{mermaid}
flowchart LR
    A["用户打开小程序"] --> B["浏览/选择平台优惠券"]
    B --> C["点击【一键复制】"]
    C --> D["弹窗提示打开对应 APP"]
    D --> E["APP 自动识别剪贴板领券"]
    E --> F["下单抵扣并产生 CPS 佣金"]
```

## 二、3 个小时极速开发时间线

作者借助 **ChatGPT 桌面版 + Codex**，在 3 小时内完成了从需求梳理、代码编写到真机发布的完整流程：

```{mermaid}
timeline
    title HP 3小时极速 MVP 推进时间线
    第 1 小时 : SPEC 需求梳理 : 苏格拉底式提问 : 明确 Non-goals : 坚决打断 AI 过度设计
    第 2 小时 : Codex 输出 PRD : 人工审核文档 : 编写核心前端页面 : 拦截 AI 自动生成的后台
    第 3 小时 : 界面样式与提示微调 : 真机测试剪贴板与跳转 : 修复 APP 唤醒逻辑 : 提交审核
```

### 2.1 第 1 小时：不写代码，只用 SPEC 梳理 MVP
许多新手用 AI 编程时最大的误区是：一句话“帮我写个外卖优惠券小程序”，AI 哗啦啦生成几千行代码，结果结构混乱、接口跑不通。

作者采用了刘小排老师在【超级 AI 大航海】中沉淀的 **SPEC 编程法**。

#### 核心需求梳理 Prompt（苏格拉底提问法）
```text
我要做一个：【外卖与生活服务优惠券聚合小程序，帮助用户一键复制口令并打开对应 APP 领券抵扣】。

请你先不要写代码。你需要像苏格拉底一样，帮助我梳理需求。
你需要一个问题一个问题地问，每次都给出带编号的选项，
直到我们能够形成一份完整的 SPEC 文档，且必须严格符合以下五个标准：

• Problem Statement（问题陈述）：精准定义目标用户在什么场景下遇到什么具体痛点。
• Proposed Solution（方案描述）：用最精简的技术路径描述解决方案。
• Technical Constraints（技术约束）：明确运行环境、依赖组件、微信平台限制。
• Non-goals（明确不做的事）：列出第一版绝对不做、坚决砍掉的所有功能。
• Success Criteria（成功标准）：上线后如何用可量化的数据判断 MVP 是否验证成功。
```

#### 实战踩坑与“打断 AI”的心法
在实际问答中，作者发现即使给了约束，Codex 依然会习惯性“发散”，比如提问：
- “是否需要支持多商户入驻申请？”
- “是否需要搭建积分商城和 VIP 会员付费等级？”
- “是否需要接入短信验证码登录和微信手机号授权？”

**关键认知**：
> Codex 思考和输出时，**人必须拥有主导权，随时可以打断它**。  
> 当作者意识到 AI 正在往复杂商业系统扩散时，立即中断生成并反问：“你刚才问的问题属于第一版核心领券动作吗？如果不是，请立即收缩回 MVP，剔除所有与领券无关的问题！”

经过这一轮约束，最终形成了一份极度精简的 SPEC 文档。

---

### 2.2 第 2 小时：Codex 写 PRD，编写核心页面与流程
1. **生成 PRD 并人工复核**：让 Codex 基于上面锁定的 SPEC 输出一份标准产品需求文档（PRD），作者逐行审查，确保没有多余页面；
2. **生成核心代码**：将 PRD 喂回 Codex，一次性生成微信小程序页面结构（WXML、WXSS、JS、JSON）；
3. **拦截 AI 的“过度开发”**：
   - Codex 在开发完核心前端页面后，表现出极其出色的主动性，“顺手”帮作者写了一套完整的本地管理后台与数据统计页；
   - 很多新手此时会陷入“AI 真厉害，我顺便把后台也弄好”的陷阱；
   - 作者果断将其搁置，不部署、不调试后台。因为第一版的核心是让用户领券，把精力浪费在后台调试上是对上线时间的极大消耗。

---

### 2.3 第 3 小时：调样式、测真机、修复制与跳转逻辑
1. **视觉细节打磨**：微调卡片阴影、文字对齐居中、优化操作提示、设计小程序简约 Logo；
2. **真机环境测试（最关键一环）**：
   - 微信开发者工具（模拟器）中点击“复制”显示 success，不代表真实手机上能成功将淘口令/美团口令写入系统剪贴板；
   - 在真机预览环境下实测：点击复制 -> 微信授权剪贴板权限 -> 切换至美团 APP -> 验证美团能否自动检测并弹出优惠券弹窗；
   - 实测确认口令格式无误、弹窗正常触发后，正式提交微信官方审核。

## 三、这次实战踩过的 5 个核心大坑

### 坑 1：小程序起名比写代码还费时间
起名是作者在整个项目周期中耗时最长的环节，远超写代码的时间：
- **个人主体的严苛限制**：作者使用个人主体注册，凡是带有“xx神券”、“xx领券”、“xx省钱”、“天天领券”等名字全部被微信驳回；
- **审核潜规则体系**：
  $$\text{商标持有主体} > \text{企业主体} > \text{个体工商户主体} > \text{个人主体}$$
  主体资质越强，命名审核的空间和词库宽容度越高。个人主体几乎无法使用高频搜索词；
- **最终妥协方案**：最终定名为【挺会过日子】——寓意“领券过日子，省钱有一手”。虽然基本放弃了微信搜索流量，但便于社群口碑传播与用户转发。

### 坑 2：备案和起名的顺序绝对不能颠倒
微信公众平台后台界面的指引存在严重的流程误导：后台界面排版往往把“小程序备案”放在显眼位置，让新手误以为先备案再起名。

```{warning}
**血泪教训**：
如果先备案，一旦后面小程序起名审核失败需要更换名称，**会导致备案流程全部失效推倒重来**！作者因此白白浪费了数天时间。
```

#### 微信小程序上线的唯一正确顺序
```{mermaid}
flowchart LR
    S1["1. 填写小程序基本信息"] --> S2["2. 准确选择服务类目"]
    S2 --> S3["3. 完成微信认证"]
    S3 --> S4["4. 最终提交小程序备案"]
```

### 坑 3：真机测试绝不能省
- 开发者工具的模拟器是基于 PC Chromium 内核与模拟环境，无法完全还原真机系统层行为；
- 真实手机涉及系统剪贴板权限弹窗、iOS 与 Android 内存管理差异、全面屏底部 Safe Area 适配；
- 特别是“复制券码并唤醒第三方 APP”的链路，必须在多台真实 iPhone 与安卓手机上亲自跑一遍。

### 坑 4：第一版绝不要手写复杂的管理后台
- Codex 极其擅长写 CRUD 代码，很容易主动给你写一套包含管理员登录、权限校验、日志记录的后台；
- 但对首版 MVP 来说，后台是巨大的负债：维护认证鉴权、防 SQL 注入、跨域配置会耗费数倍精力；
- **极简替代方案**：
  1. 直接使用**微信云开发数据库**在后台可视化修改优惠券链接；
  2. 或者直接把优惠券链接与配置写在前端静态 `config.js` / `json` 中；
  3. 每次更新优惠券直接提交新版本发布（加个发版说明），更新延迟通常只有几个小时，完全足以支撑 MVP 验证。

### 坑 5：业务链路保持单线，不要混杂
- 优惠券领取有两种常见路径：
  - 路径 A：小程序内复制口令，引导用户手动切到美团/饿了么 APP；
  - 路径 B：小程序内直接调用 `wx.navigateToMiniProgram` 跳转到美团官方外卖小程序。
- 第一版切忌把两种路径做成复杂的选项切换。作者首版只锁定一条链路，测试稳定后即可上线，将多余的精力留给用户推广。

## 四、冷启动推广路径与业务转化

产品上线只是最简单的一步，如何把产品送到真实用户手中才是关键：

| 推广阶段 | 动作与渠道 | 核心目的与产出 |
| :--- | :--- | :--- |
| **阶段 1：圈子内测** | 微信发送给 10~20 位核心好友 | 重点测试不同品牌机型、系统版本的显示与跳转稳定性 |
| **阶段 2：朋友圈与社群** | 次日在群聊与朋友圈真诚分享 | 收集第一批种子用户的易用性反馈与界面建议 |
| **阶段 3：公众号长尾** | 在自己公众号的文末贴图挂载链接 | 获取长期稳定的被动长尾流量，过滤无意义噪音 |
| **阶段 4：公域内容分发** | 小红书/知乎分享省钱攻略与领券教程 | 逐步拉升 UV，监控 CPS 佣金后台成单数据 |

**实战战报**：
产品上线一周内，在完全没有花钱买量的情况下，自然裂变累计近 300 名用户，后台成功监控到多笔外卖领券佣金结算，顺利跑通了闭环。

## 五、给独立开发者的可复用 Checklist

```text
[ ] 1. 痛点验证：这是一个你或你身边朋友每周都会遇到的真实痛点吗？
[ ] 2. 边界收敛：第一版是否只包含一个核心动作（例如：领券）？
[ ] 3. SPEC 梳理：是否用苏格拉底提问法，把 Non-goals（坚决不做的事）写死？
[ ] 4. 防范 AI 膨胀：是否在 AI 主动写后台、写登录系统时按下了暂停键？
[ ] 5. 合规顺序：是否遵循了「基本信息 -> 类目选择 -> 微信认证 -> 提交备案」的严格顺序？
[ ] 6. 真机闭环：是否在真实 iOS 和 Android 手机上测试了剪贴板与跳转全流程？
[ ] 7. 静态替代：首版能否用静态配置或云开发代替自建服务器与管理系统？
```

> **作者结语**：
> “做小程序不一定要先想清楚所有宏大构想。先找到一个真实的小需求，用 AI 做出最小版本，让它上线，让真实用户的点击告诉你下一步该做什么。对普通人来说，产品上线不是终点，而是第一次真正的开始。”
