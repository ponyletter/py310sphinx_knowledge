# 【实战复盘】阿甘：从口播到成片——参考 ChatCut 架构，用 Codex 跑通 AI 剪辑工作流

> **案例作者**：阿甘  
> **项目定位**：知识自媒体 · 个人口播短视频 AI 工业化剪辑流水线  
> **核心标签**：`口播A-roll粗剪` `ChatCut架构拆解` `火山引擎ASR` `观众任务框架` `HTML动画B-roll` `飞书审稿` `FCPXML`  
> **实战指标**：剪辑外行 3 天跑通完整链路，90% 机械工作交由 AI 处理，创作者仅需 15~20 分钟完成录制、审稿与截图，批量出片并在抖音/视频号验证  
> **关键洞察**：它不是一个简单的剪辑软件，而是一套“人只做判断、AI 干体力活”的高效作业流程。拆解优秀开源产品（ChatCut）的 MCP 协议与中间件哲学（如 `timeline.md` 与观众任务框架），能让非程序员以极低成本搭出商用级剪辑系统。

---

## 一、为什么不直接买软件，而是花 3 天拆解 ChatCut？

对于一个刚做 AI 自媒体的创作者来说，最大的卡点往往在剪辑：
- 面对镜头容易紧张，录一条 3 分钟口播包含无数个“然后、就是、那个”等垫话和口误；
- 市面外包剪辑成本高昂（单条 300~500 元），个人副业难以为继；
- 爆火的 AI 剪辑工具（如 ChatCut）虽宣称自然语言剪辑，但其实际运行痛点明显：
  1. **积分制收费极其昂贵**：生成 5 秒视频需 3 积分，加上配图与动效，剪一条 2 分钟视频的算力成本堪比找外包；
  2. **缺少代码级门禁**：纯靠 Prompt 约束极易产生时间轴错位，出了错难以追溯排查。

作者运用 **Claude（Fable 模型）+ Codex** 对 ChatCut 的开源代码、16 个 Skill 文件与 40 多个 MCP（Model Context Protocol）工具定义进行了深度逆向工程，提取出了其最核心的设计精髓。

## 二、ChatCut 架构逆向提炼的三大设计哲学

```{mermaid}
flowchart TD
    D1["精髓 1: 口播清理两步走<br/>(clean_script 机械去口癖 -> 语义二次确认)"]
    D2["精髓 2: 文本物化中间件 timeline.md<br/>(打删除线=删词，挪动行=调语序)"]
    D3["精髓 3: 观众任务框架 (Task-driven B-roll)<br/>(明确换画面目的：解构概念/看数字/见证据)"]

    D1 --> Flow["拼装低成本本地流水线"]
    D2 --> Flow
    D3 --> Flow
```

### 2.1 精髓一：口播清理必须严格分两步
- **步骤 A（机械去口癖）**：运行规则字典，高精度剔除固定口癖（“然后”、“就是”）并执行静音片段压缩（Silence Removal）；
- **步骤 B（语义级保留审查）**：重新通读上下文。系统必须识别当前这个“然后”究竟是无意义垫话，还是承担了转折与承接关系；如果是承接关系，则坚决保留，防止句子生硬拼接。

### 2.2 精髓二：人类可读的中间件格式（`timeline.md`）
- 传统剪辑工具直接让大模型操作冰冷复杂的 JSON 时间轴，容易产生格式崩溃；
- ChatCut 将语音转录结果物化为一份结构清晰的 **Markdown 文档（`timeline.md`）**：
  - 用户想删掉一句话，直接在 Markdown 里打上 `~~删除线~~`；
  - 想调整论述顺序，直接剪切粘贴挪动行；
  - 最终一条 `apply_script` 命令，底层自动将 Markdown 修改无损映射回剪辑时间线。

### 2.3 精髓三：“观众任务”框架（为什么换画面？）
在插入 B-roll（补空画面/动效）之前，大模型必须先回答：**“观众此刻需要什么帮助？”**
- 是为了理解抽象概念？（配流程架构图）
- 还是想看到关键量化数字？（配数据滚动卡片）
- 还是需要可信的真实证据？（配软件实操截图/录屏）
- **如果答不上来，坚决不切画面，保持口播主体不动**，避免出现画面花哨但信息脱节的乱切镜头。

## 三、阿甘的 6 步 AI 剪辑生产线（人机分工极简流）

作者将 GitHub 开源剪辑 Skill、火山引擎 ASR、飞书 CLI 与 Codex 串联，搭建了一条全自动生产线：

```{mermaid}
sequenceDiagram
    autonumber
    actor Creator as 创作者 (人工)
    participant Codex as Codex 主控引擎
    participant Volc as 火山引擎 ASR
    participant Feishu as 飞书协作文档

    Creator->>Codex: 1. 录制并提交 2~5 分钟口播原始视频
    Codex->>Volc: 2. 高精度语音转录并标注口误
    Codex->>Creator: 3. 生成本地网页: 试听并勾选删除口误 (人工确认 1)
    Codex->>Codex: 4. 输出 FCPXML 完成 A-roll 粗剪
    Codex->>Feishu: 5. 推送智能分镜表至飞书文档
    Creator->>Feishu: 6. 像审稿一样划词批注微调分镜 (人工确认 2)
    Codex->>Codex: 7. 根据分镜生成 HTML 代码并渲染为 B-roll 动画
    Creator->>Codex: 8. 补充关键真实录屏/截图 (人工确认 3)
    Codex->>Creator: 9. 自动合成并导出最终成片
```

### 3.1 零成本 B-roll 替代方案：HTML 动画代码
许多人以为 B-roll 必须花大价钱调用 Runway、Sora 或 Midjourney 生视频。
阿甘探索出了一条**极低成本的优雅解法**：
- 让 Codex 根据分镜直接编写独立的 **HTML/CSS/JS 动态页面**（如数字递增计数器、流程箭头流动、代码高亮浮层）；
- 本地无头浏览器（Puppeteer）自动将 HTML 录制为 WebM/MP4 视频片段；
- 零额外算力成本，且文字清晰锐利，天然适配科技与商业自媒体。

## 四、真实发布数据复盘：打破无意义的完美主义

视频跑通发布后，作者在抖音与视频号进行了双平台分发，后台数据带来了极具颠覆性的认知：

### 4.1 流量漏斗的诊断分析
- **触达充足**：抖音播放量超越同类作者 $93.95\%$，视频号超越 $74.5\%$，说明平台算法愿意给予充足推流；
- **前 3 秒留人优秀**：视频号“3 秒以上播放率”达到 $48\%$（超越同行 $21\%$），说明开头的标题与第一句话已经成功吸引了近半数用户驻足；
- **致命卡点在中段完播率**：虽然开头留住了人，但整片完播率仅 $4.2\%$，平均播放时长只有 $10.6$ 秒。

### 4.2 核心反思与迭代指导
> **作者复盘教训**：  
> “在剪片时，我花了大量时间纠结‘这个动画配色高级不高级’、‘阴影参数要不要调大’。但数据狠狠打醒了我——绝大部分观众看到第 12 秒就已经划走了，根本没看到后面精心设计的动效！**真正需要动刀的是 3 秒之后的中段节奏、信息密度以及整体片长**。脱离真实数据反馈的自嗨式完美主义，就是在浪费生命。”

### 4.3 平台人群差异洞察
- **视频号**：完播率和平均播放时长明显优于抖音，且用户更倾向于深度的长逻辑讲述；
- **抖音**：用户极度没有耐心，必须大幅砍掉非核心论据，将 3 分钟的视频压缩到 60~90 秒之内，并将节奏提速至极致。
