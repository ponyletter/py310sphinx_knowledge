# 全自动 CI/CD 门禁与真实生产级 Bug 攻防实录

在软件交付中，**没有被测试保护的代码等同于负债；而没有在真实生产中经历过黑产洗礼的系统算不上成熟**。本节详细公开 24goods 的 GitHub Actions 全自动多阶段流水线，并深度复盘 5 个极其隐蔽但破坏力极大的生产级 Bug 与攻防修复方案。

## 1. 工业级 GitHub Actions CI/CD 流水线

系统严禁在未经自动化门禁验证的情况下直接发布镜像。每一次代码合并（PR），云端 CI 将自动执行全套严苛检验：

```{mermaid}
flowchart TD
    PR["开发者 / AI 提交 PR"] --> Gate1["并发门禁 1: 后端深度质检<br/>(Ruff Linter/Formatter + 真实PG/Redis环境 Pytest + Bandit + pip-audit)"]
    PR --> Gate2["并发门禁 2: 前端工程质检<br/>(pnpm lint + vue-tsc 类型严检 + Vitest + 77KB首包体积预算)"]
    PR --> Gate3["并发门禁 3: 安全渗透与机密扫描<br/>(Semgrep SAST扫描 + Gitleaks代码凭证扫描)"]

    Gate1 & Gate2 & Gate3 --> Gate4["集成门禁 4: 容器构建与 Trivy 漏洞扫描<br/>(多架构无特权镜像打包 + CVE安全扫描)"]
    Gate4 --> Gate5["终极门禁 5: 真实环境端到端 E2E Smoke 全链路冒烟<br/>(启动Caddy+API+Delivery全套栈/真实模拟买家浏览/聊天议价/付款/发卡解密)"]
    Gate5 --> Deploy["自动推送到 GitHub Packages (GHCR)<br/>演示站 Systemd 自动拉取灰度发布"]
```

### Action 版本固定铁律
为抵御 GitHub Actions 第三方组件遭遇恶意供应链投毒，所有 Workflow 中的 Action 必须锁定完整的 40 位 Commit SHA：
```yaml
# .github/workflows/ci.yml
- name: Checkout repository
  uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
```

## 2. 真实生产级重大 Bug 战报与攻防复盘

以下 5 个典型 Bug 均取材于 24goods 在真实多轮审计与灰度测试中捕获的核心缺陷，具有极高的工程借鉴价值。

---

### 💥 战报 1：购物车手续费多商品逐行向上取整（CEIL）舍入差
- **发现背景**：买家在购物车同时选中 5 件 1.01 元的小额虚拟卡密，前端显示的合计金额是 **¥5.21**；但买家点击付款跳转到收银台时，网关却显示要求付款 **¥5.25**！买家认为平台存在欺诈加价，放弃付款。
- **深层成因分析**：
  - 后端在 `orders/checkout.py` 中为防范商家每笔子订单少收一分钱，对每个商品行独立做了向上取整计算手续费并逐行相加：
    $$\text{Line\_Fee}_i = \lceil 1.01 \times 3\% \rceil = \lceil 0.0303 \rceil = 0.04 \text{ 元}$$
    5 件商品累计手续费：$5 \times 0.04 = 0.20$ 元。总金额 = $5.05 + 0.20 = \mathbf{5.25 \text{ 元}}$；
  - 前端在 `stores/cart.ts` 中却先将 5 件商品小计求和为 5.05 元，再执行了一次总的向上取整：
    $$\text{Frontend\_Fee} = \lceil 5.05 \times 3\% \rceil = \lceil 0.1515 \rceil = 0.16 \text{ 元}$$
    总金额 = $5.05 + 0.16 = \mathbf{5.21 \text{ 元}}$；
  - 根据数学次可加性（$\lceil a+b \rceil \le \lceil a \rceil + \lceil b \rceil$），汇总后再取整必然小于逐行独立取整之和！
- **攻防修复**：
  前端必须严格对齐后端的算法模型。在客户端计算展示总价时，严禁使用“总价 $\times$ 费率”，而必须遍历勾选的商品行，逐行执行 `(sub_i * permille + 999n) / 1000n` 累加，保证买家在购物车看到的数字与收银台分毫不差。

### 💥 战报 2：切换支付方式引发 `FeeChannelMismatch` 409 永久锁死
- **发现背景**：买家在订单详情页首先点击“支付宝（3% 手续费）支付”，系统生成了支付链接。买家发现支付宝余额不足，返回页面切换选中“USDT（0% 手续费）支付”，结果系统立即弹出报错：“*The payment fee changed; please recreate the order*”，之后该订单再也无法付款，彻底锁死！
- **深层成因分析**：
  - 在 `orders/service.py` 中，当买家首次点击支付时，`order.channel` 被打上了 `'zpay_alipay'` 标记；
  - 当买家切换为 USDT 重新发起支付时，系统检测到新渠道费率（0‰）与订单记录费率（30‰）不符。由于 `order.channel is not None`，代码假定“旧支付链接已流出公网，为防旧链接被以旧金额支付”，直接抛出 409 异常阻断；
  - 然而在 C2C 协商议价或使用专属优惠券的场景下，买家根本无法自行“重新下单”！
- **攻防修复**：
  重构支付状态机：在订单尚未真正在网关完成结算前，允许买家调用安全的换通道逻辑。只要在数据库排他锁下确认旧渠道尚未完成付款，立即注销/作废旧的网关 Attempt，以新渠道的费率重算 `fee_minor` 与 `amount_minor` 并递增 `order.version`，允许买家顺畅换用 USDT 完成支付。

### 💥 战报 3：订单详情页支付方式切换时总价缺乏实时响应联动
- **发现背景**：在待支付详情页上，虽然提供了支付渠道选择列表（`<PayChannelPicker>`），但买家无论在支付宝与 USDT 之间如何切换，下方的明细金额与总价毫无变化，必须点击“立即付款”跳转后才能看到变化，体验极度反直觉。
- **攻防修复**：
  在 `OrderDetailPage.vue` 中建立响应式计算属性 `realtimeTotals`，监听当前激活的 `site.channel?.permille`。一旦用户切换单选框，界面上的手续费标签、手续费金额以及底部的吸底结算栏金额立即毫秒级联动重算展示，给买家最透明的确定感。

### 💥 战报 4：USDT 关单反查过度依赖内存 Redis 导致的掉单风险
- **发现背景**：系统设计了“取消订单前先向网关回查（Query Before Close）”的安全规则，防止买家刚付完款订单就被后台超时取消。但在 USDT 渠道中，由于 BEpusdt 网关仅支持通过 `trade_id` 查单，系统将 `trade_id` 存放在了 Redis 的 `usdt:attempt:{order_no}` 键中。
- **隐患推演**：
  一旦 Redis 实例发生热重启、内存驱逐（Eviction）或网络瞬断，`load_attempt()` 返回 `None`，关单逻辑误以为该订单“从未开启过支付交易”，直接在数据库中将订单强行置为 `cancelled` 并释放卡密库存！而买家实际上已经在区块链链上转出了真实的 USDT！
- **攻防修复**：
  **关键业务凭据必须入库持久化**。在 `orders` 与 `checkouts` 表中新增物理列 `usdt_trade_id`，在每次调用网关生成链上交易的第一时间，将其写入 PostgreSQL 数据库落盘；关单反查时优先以数据库中的持久化 `trade_id` 为准，杜绝因内存缓存丢失导致的错杀订单。

### 💥 战报 5：聊天议价接受报价未明示支付手续费（反向加价客诉）
- **发现背景**：客服与买家在聊天流中友好协商，最终达成一致以 100 元成交。买家点击确认弹窗：“以 ¥100.00 接受该报价？”，确认后被直接跳转到收银台，金额却赫然显示为 **103.00 元**。买家大怒，认为遭遇了隐形宰客。
- **深层成因分析**：
  报价卡片记录的是商户的货品净价（100 元）。后端在转为订单时，自动附加了默认支付网关的 3% 手续费（3 元），而前端在确认环节未向买家展示“商品 100 元 + 支付渠道手续费 3 元 = 实际需付 103 元”的拆解明细。
- **攻防修复**：
  在聊天界面的接受报价确认弹窗中引入 `<FeeLines>` 费用明细展示，并在买家确认前允许其自主勾选支付通道（如告知选择 USDT 可享 0 手续费 100 元实付，选择支付宝收取 3 元手续费）。信息完全对称后，客诉率降至归零。
