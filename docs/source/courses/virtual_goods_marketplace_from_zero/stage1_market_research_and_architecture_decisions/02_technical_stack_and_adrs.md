# 核心技术选型与关键架构决策记录 (ADRs)

在架构设计中，**每一次“选择不使用某种热门技术”往往比“使用某种技术”更能体现工程的克制与务实**。在 24goods 的立项之初，我们通过严格的架构决策记录（Architecture Decision Records, ADRs）确立了整套技术选型底座。

---

## 1. 核心技术栈全景图

```
24goods 工业级技术拓扑
│
├── 接入与静态分发: Cloudflare (WAF/Bot) ──► Caddy 2 (自动 HTTPS / 纯静态SPA托管 / 反向代理)
│
├── 业务中枢 (API): FastAPI (Python 3.12 异步高并发) + SQLAlchemy 2.0 (Asyncpg) + Alembic
│
├── 隔离金库 (Delivery): 独立常驻后台消费者进程 (完全禁止公网出网 / 唯一持有解密私钥)
│
├── 状态与存储:
│   ├── PostgreSQL 16 (开启 FORCE RLS 强租户隔离 / 列级权限收敛 / 记账平衡触发器)
│   └── Redis 7 (ACL 角色隔离 / 速率限制 / 状态缓存 / SSE Pub-Sub 消息队列)
│
└── 前端工作区 (pnpm monorepo):
    ├── apps/web: 买家端 (Vue 3 + Vant 4 移动端优先设计, 375px 基准)
    ├── apps/admin: 运营管理后台 (Vue 3 + Element Plus 桌面高密管理)
    └── packages/shared: 共享类型、金额安全函数 (BigInt Fen 计算)、SSE 客户端与 i18n
```

## 2. 关键架构决策记录 (Key ADRs)

### ADR-009：摒弃 Nuxt / Next.js SSR，全面拥抱纯静态 Vite SPA
- **背景与困境**：现代前端团队习惯使用 Nuxt 3 或 Next.js 服务端渲染（SSR）来优化 SEO。然而在生产环境中，Node.js SSR 运行时会带来显著的痛点：
  1. **内存黑洞**：单个 Node SSR 进程常态占用 150MB~300MB 内存，这对于我们控制在 2GB 内存配额的服务器而言极其危险；
  2. **双端水合（Hydration）报错**与跨国高延迟下的白屏风险；
  3. **Node 运行时安全漏洞与供应链投毒**。
- **决策结论**：**生产环境彻底摒弃 Node 运行时**。前端编译为纯静态 HTML/JS/CSS，直接由 Caddy 高性能静态分发。初始打包体积压缩至 **77 KB (gzip)**，首屏加载接近瞬时完成。
- **SEO 替代方案**：针对商品页的搜索引擎抓取，采用后端 FastAPI 的轻量级爬虫适配路由（根据 User-Agent 识别 Googlebot/Bingbot 并直接返回预渲染的基础静态 HTML 和 Schema.org JSON-LD），兼得极简架构与 SEO 诉求。

### ADR-010：采用 SSE (Server-Sent Events) 替代复杂 Centrifugo / WebSocket
- **背景与困境**：闲鱼式即时聊天、订单状态实时变更（待支付 $\to$ 已支付 $\to$ 已发货）需要实时通知。传统方案通常引入 Centrifugo、Socket.io 或独立 WebSocket 服务器。但这带来了双向长连接维护、负载均衡粘性会话与断线重连握手的高昂成本。
- **决策结论**：**全面采用基于 HTTP/2 的 Server-Sent Events (SSE)**。
  - **单向下发极简架构**：客户端发送消息走标准 HTTP POST 请求，服务端通过 Redis Pub/Sub 将事件推送给 SSE 客户端；
  - **原生浏览器抗弱网**：原生 `EventSource` 自带毫秒级断线自动重连，无需第三方庞大 SDK；
  - **连接复用**：在 HTTP/2 下多个 SSE 通道无缝复用底层单个 TCP 链路，连接开销近乎为零。

### ADR-011：内置深度定制客服收件箱，拒绝引入 Chatwoot / 第三方外挂
- **背景与困境**：许多系统通过嵌入 Chatwoot、Crisp 等第三方客服系统来解决沟通问题。
- **决策结论**：**在主干代码库中自主研发一体化客服收件箱（CS Inbox）**。
  - **强关联业务状态机**：买家在聊天窗中不仅能发文本和图片，更能直接互动**动态报价卡片、商品卡片、订单状态卡片、解密卡密卡片与买家凭据输入表单**；
  - 外挂第三方客服系统完全无法实现“在聊天流中无缝原子化下单并完成付款校验”的极致流畅体验。

### ADR-012：双进程架构实现卡密物理隔离（业务 API vs 交付 Worker）
- **背景与困境**：绝大多数系统在同一个 Web 进程中处理用户注册、商品浏览与卡密解密。一旦 Web 代码库中存在任意一处高危漏洞（如任意文件读取、反序列化或依赖库 RCE），攻击者就能直接从当前进程内存或环境变量中提取解密密钥。
- **决策结论**：**将系统拆解为物理级双进程拓扑**。
  - **API 进程**：暴露在公网，处理 HTTP 请求，仅持有公钥，只能**加密**卡密，数据库连接仅赋予 `app_api` 最小权限（无权读取解密私钥，且卡密表列级只读）；
  - **Delivery 进程**：常驻后台消费 Outbox，**Docker 网络配置为 `internal: true`，物理禁止外网出网访问（No Egress）**；只有该进程挂载解密主密钥（KEK）。即使前端 API 容器全盘失陷，攻击者也绝对无法通过网络渗透到 Delivery 内部拿到私钥。

## 3. 面向开发者的非协商安全底线（Invariants）

在整个生命周期中，项目制定了 **11 条不可动摇的安全铁律**，任何违反下列原则的代码 PR 必须在 Review 阶段一票否决：

1. **卡密明文永不落盘、不打印、不随响应暴露**：只有 `app/core/cardvault.py` 能密封/开启卡密，后台界面一律脱敏（`mask()`）；
2. **支付回调绝非真相**：必须依次回调校验：恒定时间算法签名 $\to$ 商户 ID 匹配 $\to$ `Decimal` 绝对金额匹配 $\to$ 状态检查 $\to$ 服务端主动反查网关 $\to$ 行级排他锁 $\to$ `UNIQUE(channel, gateway_trade_no)` 幂等入账；
3. **价格与金额由服务端绝对掌控**：客户端传来的任何价格字段严禁采信，改价必须通过带审计与版本号的服务端流程；
4. **多租户数据强隔离**：每一条租户数据查询，必须在存储库层与 PostgreSQL RLS 双重过滤 `tenant_id`；
5. **代码库永存无机密**：使用 `.env`（git 忽略），CI 门禁常态运行 `gitleaks` 扫描；
6. **文件上传视作恶意攻击**：Magic Bytes 强校验文件头、Pillow 重新编码、剥离 EXIF、独立存储随机 Key 并由独立无执行权限域名分发；
7. **数据、密钥与支付逻辑严禁部署在受限法域**；
8. **前端运行时零第三方 CDN / 外部资源引用**（防止供应链投毒并保障全球直达）；
9. **GitHub Actions 必须锁定 Commit SHA**（加注版本注释，防止 Action 供应端被篡改）；
10. **每进程最小特权原则**：API 与 Delivery 使用互斥的独立环境文件与 Redis ACL 账号；
11. **静态扫描不可替代独立审计**：进入真实生产真实资金前必须通过渗透测试。
