# 全球与国内虚拟商品平台深度调研与竞品全景

在立项开发 **24goods** 之前，我们组织了专门的调研小组对全球范围内主流的开源与商业化虚拟商品售卖系统进行了深度拆解。本节将从**系统定位、数据安全、履约模式、支付网关、议价能力与分销白标**六大维度展开横向评测，阐明现有产品的固有缺陷以及 24goods 的创新破局点。

## 2. 传统发卡系统与商业 SaaS 的深层缺陷

### 缺陷一：脆弱的“明文卡密库”防线
绝大多数国内站长使用的开源发卡系统，其卡密表（`cards` / `card_stocks`）设计极为简陋，卡密字段通常为 `VARCHAR(255)` 或仅经过简单的可逆加密（如 `base64` 或硬编码在 `.env` 中的固定 AES 密钥）。
- 一旦 Web 应用遭遇诸如 CVE-2023 框架漏洞、弱口令上传 Webshell 或运维失误将 `.sql.gz` 备份文件放置在 Web 根目录下，**攻击者即可在几秒钟内拖出全部卡密资产并在二级市场倒卖套现**。
- 商家不仅损失货物，更面临失信与挤兑危机。

### 缺陷二：无法承接“个性化代充与数字化定制服务”
当前市场上高客单价、高复购率的虚拟商品，正在从“标准化卡密”（如爱奇艺月卡）向**“个性化定制与代充服务”**转变（例如：ChatGPT Plus 账号定制充值、Claude Pro 绑定、海外 Apple ID 定制、Cursor / API 额度升级等）。
- 这类服务要求买家在下单时（或下单后）提交专属信息（如邮箱、密码、2FA 验证码、临时授权链接）。
- 传统发卡系统完全不具备字段动态收集能力与即时在线交互能力；商家通常只能在商品简介写“购买后加微信/TG”，这直接打断了自动化闭环，跳单率极高。

### 缺陷三：假支付漏洞与浮点数对账灾难
- **通知伪造**：许多聚合支付（易支付类）网关仅凭异步回调（Notify）的签名就直接将订单置为已支付，黑客可通过撞库或利用网关早期版本弱密钥伪造通知，系统不向官方支付网关反向回查（Server-to-Server Re-query），导致未付先发。
- **浮点数计算漏洞**：部分系统在计算商品手续费、优惠折扣或多货币换算时，直接在代码中使用 IEEE-754 浮点数（如 Python `float`、PHP `float`、JS `Number`），产生精度丢失。更有甚者直接采信客户端传来的 `amount` 字段，攻击者通过抓包篡改支付金额为 `0.01` 元即可提走百元商品。

## 3. 24goods 的创新定位与设计原则

针对上述痛点，**24goods (Kesiv)** 确立了不可动摇的**四大设计原则**：

### 原则 1：卡密零明文落盘，业务与交付物理分离
- **信封加密机制**：商品上架录入卡密时，Web API 只能使用**公开密钥（Public Key）**将卡密加密存入数据库；
- **独立交付进程**：后台常驻一个无外网出网权限的独立进程 `delivery`。**全系统唯独该进程持有解密私钥**；买家只有在支付确认、订单状态流转为 `paid` 并持有一次性访问凭证（Access Code）通过内部受限接口请求时，交付进程才会解密卡密，全程不写日志、明文在内存中即时销毁。

### 原则 2：闲鱼式砍价沟通 + 严密的 HMAC 防篡改报价
- 买家可随时在商品详情页唤起即时聊天沟通；
- 客服/卖家可在对话流中发起**自定义改价卡片**（指定商品、数量、最终优惠总额）；
- 报价卡片由服务器根据版本号、会话 ID、金额计算 **HMAC-SHA256 签名**，杜绝客户端修改 DOM 恶意压价提交；买家点击“接受报价”后原子化生成待支付订单。

### 原则 3：支付“先查后结”、复式记账与手续费透明
- **支付异步通知绝非真相**：异步回调仅视为“推进提示”；系统在确认签名后，必须由服务器出网向支付网关发起主动回查，确认金额（必须为绝对精确的 `Decimal`，一分不差）与流水号后，方可启动行级锁（`FOR UPDATE`）推进状态机；
- **复式记账审计**：每笔订单的支付、退款、分销商分润、手续费均通过会计复式记账账本写入流水，数据库触发器严格校验借贷平衡（$\sum=0$），资金流水永久可审计。

### 原则 4：彻底合规与境外出海架构
- 鉴于虚拟资产与加密货币在部分法域的合规风险，24goods 严格坚守**“数据、密钥、业务逻辑完全境外托管”**准则，数据中心选用日本等离岸机房，接入 Cloudflare 屏蔽不可靠流量，保障系统的纯粹性与全球化扩展能力。
