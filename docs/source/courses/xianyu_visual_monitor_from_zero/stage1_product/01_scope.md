# 01 从卖家痛点到可验收需求

## 先把问题描述准确

本项目服务于需要兼顾其他工作的卖家：新客户首次咨询容易漏看，常见问题反复回答，手机与网页的已读状态还会互相影响。需求不是“把所有消息抓下来”，而是及时发现可见的新来信，执行可解释的回复，并让店主知道哪些步骤无法确认。

最小闭环是：已有登录桌面 → 截图 → 识别客户行 → 与持久化状态比较 → 新客户邮件／关键词规则 → 屏幕操作 → 核验 → 返回列表。每次自动输入都有目标、触发事件和结果证据。

|需求|交付标准|容易误解的地方|
|---|---|---|
|首次新客户提醒|同一客户只建立一个首次提醒任务，首次无红点后续有来信仍可补建|“本次新观察”不等于平台第一次联系|
|手机已读同步|仅红点消失不算新增来信|总未读数不能替代逐行状态|
|固定关键词回复|规则命中、上下文仍成立才发送|自动模式也可能因规则审核或置信度转审核|
|文字后图片|先核实文字，再选择默认图片；不重复已核实文字|选择文件不等于上传成功|
|回复后退出会话|F5 后确认健康列表和未选中会话|不能点击系统会话“占位”|
|故障可追溯|记录任务阶段、错误原因和单独的发送／返回结果|网页显示气泡不等于接收端必然收到|

## 第一版的边界

采集范围是已登录桌面当前可见的行和校准的聊天区域。昵称不是稳定平台 ID，OCR 不是完整聊天记录。扫码、验证码由人处理。当前固定规则并不是已经接入大模型的智能客服。

把范围写进需求，能避免在销售或验收时承诺“完整历史”“永不漏消息”“任何账号即开即用”。如果连续两条消息在截图间隔内出现且最后画面完全相同，单靠像素无法证明中间发生过什么。

## 从 0 到 1 的里程碑

1. 单张离线截图读准姓名、预览、角标、时间。
2. 只观察、不操作，持久化客户与状态转换。
3. 建立历史基线，演练首次提醒和去重。
4. SMTP 连通与一封受控测试邮件。
5. 仅审核模式，人工核对规则与目标。
6. 单条文字受控发送，核实结果后 F5。
7. 默认图片受控发送，检查延迟与重复。
8. 独立桌面、服务托管、性能基准和故障演练。

**练习与交付**：为每一阶段写出“触发、预期结果、不能据此证明的事实、留存证据”。不要把第 1 阶段 OCR 成功当作第 8 阶段交付完成。
