# 21 集中控制台、容量规划与权限

## 管理面可以集中，输入执行面要隔离

未来控制台应展示每个账号的显示号、版本、最后有效截图时间、登录状态、队列、暂停原因、待审核和最新回执；统一入口不意味着所有账号共用一个鼠标键盘。账号异常只暂停该账号，平台级紧急停止才作用全局。

|控制项|建议约束|
|---|---|
|批量规则发布|显示 diff、作用账号、预计影响；先在少量账号预览|
|自动发送开启|逐账号授权、记录操作者；不可等同“批准全部历史任务”|
|批量暂停|幂等、可审计；标明是否保留进行中的不可逆动作|
|诊断导出|默认脱敏，不自动汇总所有客户截图|
|集中登录|管理员管理权限与平台账号登录权限分开|
|资产库|版本和 hash 绑定账号可见范围，避免串图|

## 容量不能仅按 8 核估算

Chrome 内存、截图分辨率、OCR 首次读取比例、图片匹配频率、数据库 IO、温度降频都影响容量。先用两个实例测 CPU 核秒、RSS／PSS、周期和 P95 延迟，再决定是否继续增加。

```text
CPU负载估算 = Σ(账号每周期实际消耗的CPU核秒 / 采集周期秒)
内存预算 = 系统保留 + 每个Chrome/profile工作集 + OCR模型进程 + 数据库 + 峰值余量
```

这不是用墙钟 9 秒除以 6 秒的简单线程数计算；并行 OCR 会占多核。多个账号都绑定 CPUs 4–7 时仍会相互争用。共享 OCR 服务可能减少模型副本，但会引入跨账号队列、公平调度、输入序列化与数据隔离，需要新接口和测试。

## 建议的扩展顺序

单账号长时间回归 → 两账号完全实例隔离 → 几台板的批量版本管理 → 集中只读健康面板 → 经授权的集中配置／审核 → 有必要时再迁移共享多租户。每一步都以故障隔离和实际负载数据为放行条件。

**交付**：一张容量记录表和账号隔离测试矩阵；不要在没有测量时承诺“一块板支持几十账号”。
