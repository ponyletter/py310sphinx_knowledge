# RAG 不是只靠向量库：缓存、关键词、重排序与模型网关怎么组合？

> 短视频主题：RAG 不是只靠向量库：缓存、关键词、重排序与模型网关怎么组合？
> 资料核验与更新：2026-09-24

RAG（检索增强生成）不是“把文档切块，再放进向量数据库”就结束。一个更可靠的知识问答链路，还要把权限、缓存、关键词检索、向量检索、候选合并、重排序、模型调用和来源回链安排在各自的位置。本文面向第一次接触 RAG 的读者，先看一条完整路径，再理解每个组件为什么存在。

文中的图均为本课程制作的 AI 辅助教学示意图，不是厂商产品的原始界面或性能承诺；它们用来解释数据流和职责边界。

## 阅读边界

本文依据课程研究笔记、结构计划和发布文案整理。产品能力、版本、价格、延迟和平台规则可能变化，实践前应以当前官方资料和真实环境为准。这里的“LLMWiki”是可版本化、可审阅 Markdown 知识层的实践称呼，不代表一个统一的行业标准产品。

## 先打破一个误区：有向量库，为什么还会答错？

向量检索擅长寻找“意思相近”的片段，却不天然保证编号、条款、权限和版本都准确。比如问题里有一个精确的合同编号，语义相近的段落可能比真正包含该编号的段落更容易被召回。因此，“已经入库”只代表完成了准备工作，不代表检索、筛选和回答链路已经闭环。

```{figure} images/scene01_img01_misconception.png
:alt: 语义相近的片段可能错过精确编号，说明向量库不是完整 RAG
:width: 100%

图：切块和向量化只是起点；精确字段仍需要关键词、权限和来源校验。
```

对零基础读者，可以把它想成查资料：向量像“理解大意的检索员”，但遇到订单号、法规条款或产品型号，还要有能逐字核对的查找方式。

## 一条问题会经过哪些层？

一个可复用的心智模型是：先做权限过滤，再看精确缓存；没有直接命中时，关键词检索和向量检索并行召回候选，随后合并、重排序，只把少量可追溯的原文交给 LLM，最后把答案和来源一起返回。

```{figure} images/scene02_img01_flow.png
:alt: RAG 从权限和缓存到双路召回、重排序、模型与来源答案的完整流程
:width: 100%

图：RAG 是一条分工明确的数据流，而不是某个单独的向量数据库。
```

这条路径的关键不是组件越多越好，而是每层只承担自己擅长的工作。尤其不能因为缓存命中很快，就跳过租户权限、知识版本或失效规则。

## 关键词检索和向量检索：不是二选一

关键词检索适合产品型号、字段名、编号、法规条款和缩写；它关注字面命中。向量检索把问题和文档编码成向量，更适合处理同义改写和自然语言表达。真实问题往往同时需要“找得准”和“听得懂”，所以两路召回通常并行发生。

```{figure} images/scene03_img01_keyword.png
:alt: 关键词检索通过编号和原词命中精确字段
:width: 100%

图：关键词像查字典，适合逐字核对编号、型号和条款。
```

```{figure} images/scene03_img02_semantic.png
:alt: 向量检索通过语义相似度召回不同说法的相关片段
:width: 100%

图：向量像理解意思，能覆盖同义表达，但需要后续筛选来降低误召回。
```

把两类结果合并后，还需要统一去重、保留来源信息，并重新应用权限和知识版本边界。Azure AI Search 的混合检索文档就是一个公开的工程例子：全文与向量查询并行执行，再用 RRF 等方法融合排序。

## 重排序：候选集里的“复试官”

第一阶段召回的目标是不要漏掉可能相关的内容，因此候选可以相对宽；重排序（reranker）的目标则是从这批候选中判断“问题和片段是否真的匹配”，把最值得给模型看的少量证据排在前面。它不是重新遍历整个知识库，也不是模型调用本身。

```{figure} images/scene04_img01_rerank.png
:alt: 重排序把较大的候选集合压缩成少量高相关证据
:width: 100%

图：重排序像复试官，只对已召回的候选逐条复核，再交给 LLM 更干净的上下文。
```

候选过多会增加上下文噪声和模型成本；候选过少又可能在第一阶段就漏掉答案。工程上要用离线评测和真实查询观察这两个阶段，而不是只看一个“相似度分数”。

## 三层缓存：快，但不能绕过边界

缓存可以减少重复计算，却不是检索的替身。精确缓存复用同一规范化问题的结果；语义缓存尝试复用相近意图；检索缓存复用查询向量、关键词结果或候选集合。三者都必须携带权限、租户、知识版本和失效信息。

```{figure} images/scene05_img01_exact_cache.png
:alt: 精确缓存按规范化问题和权限版本直接复用答案
:width: 100%

图：精确缓存命中最快，但前提是问题、权限和知识版本都一致。
```

```{figure} images/scene05_img02_semantic_cache.png
:alt: 语义缓存按相近意图复用结果并设置阈值和失效策略
:width: 100%

图：语义缓存更灵活，也更需要阈值、版本和可解释的命中策略。
```

```{figure} images/scene05_img03_retrieval_cache.png
:alt: 检索缓存复用查询向量或候选集合但仍需重新应用权限边界
:width: 100%

图：检索缓存能省掉部分召回成本，但不能把旧的权限判断当成永久有效。
```

最容易出事故的做法，是把“命中缓存”理解为“无需再检查权限”。安全的缓存键和失效策略，往往比缓存本身的命中率更重要。

## pgvector 和 Milvus：按约束起步，不宣布冠军

如果系统已经使用 PostgreSQL，并且事务、权限过滤和业务数据紧密相连，可以先评估 pgvector。它是 PostgreSQL 扩展，支持精确和近似最近邻，也能和 PostgreSQL 全文检索组合做混合检索。

```{figure} images/scene06_img01_pgvector.png
:alt: pgvector 将向量检索放在 PostgreSQL 事务和权限数据旁边
:width: 100%

图：已有 PostgreSQL 生态时，pgvector 的优势是减少系统边界和数据同步。
```

如果向量规模、多向量字段或混合检索形态更复杂，可以评估 Milvus；但还要一起考虑运维、成本、延迟和团队经验。Milvus 文档提供全文 BM25、多向量搜索以及加权或 RRF 合并的能力描述。

```{figure} images/scene06_img02_milvus.png
:alt: Milvus 面向多向量和混合检索场景提供独立的检索能力
:width: 100%

图：规模和检索形态变复杂时，专用向量数据库可能更合适，但并不自动意味着更好。
```

真正的第一轮选型问题是：数据在哪里、权限在哪里、查询形态是什么、团队能稳定运维哪一种方案，而不是谁的名气更大。

## LLMWiki、GraphRAG 和模型网关各管什么？

LLMWiki 可以理解为一层可审阅、可版本化的 Markdown 知识维护流程；GraphRAG 则围绕实体、关系、社区摘要和跨文档问题建模。前者强调知识如何被人维护，后者强调关系和全局主题如何被检索，两者都不是向量数据库的替代品。

```{figure} images/scene07_img01_llmwiki.png
:alt: LLMWiki 通过版本化 Markdown 和人工审阅维护知识层
:width: 100%

图：把知识当作可审阅的版本化内容，便于追踪谁改了什么、何时生效。
```

```{figure} images/scene07_img02_graphrag.png
:alt: GraphRAG 通过实体关系和社区摘要支持跨文档问题
:width: 100%

图：GraphRAG 适合关系密集或需要全局主题的问题，但构建和更新成本也更高。
```

模型网关处在另一层：它统一模型接口、路由、预算、限流、日志、重试或回退。以 Cloudflare AI Gateway 为例，它治理的是模型调用，不负责文档切块、建向量索引或构建知识图。

## 小结：好 RAG 要能回到来源

一条清晰的 RAG 路线可以浓缩成：权限先行，缓存分层；关键词和向量并行召回；重排序压缩上下文；模型网关治理调用；答案最后回到可核对的原始来源。这样看，向量库只是检索链路的一环，而不是整个系统的答案保证。

```{figure} images/scene08_img01_summary.png
:alt: 权限、缓存、关键词、向量、重排序、模型与来源答案组成可追溯 RAG 闭环
:width: 100%

图：最终判断标准不是“接了哪个数据库”，而是答案能否在正确权限下回到来源。
```

如果你要开始做第一版，先选一条真实问题链路，记录每一层的输入、输出、权限和失效条件，再用小规模评测比较召回、重排序、缓存和来源回链的效果。
