## 阅读边界

本文依据课程研究笔记、讲解结构、发布文案和视频最终验证结果整理。Git、SVN、代码托管平台、流水线、服务周期和产品功能都可能变化；实际迁移或采购前，应再次核对官方文档、公告、权限模型和当前套餐。本文不把 GitHub、GitLab、Gitee、CNB 的差异简化为“谁一定更好”，而是提供一套可以落地验证的选择框架。

## 先分清两层：版本控制工具和托管平台

很多初学者会把 Git 和 GitHub 当成同一个东西。更准确的分层是：Git、SVN 负责记录代码版本；GitHub、GitLab、Gitee、CNB 则是在仓库之上提供协作、审查、自动化和交付能力的平台。

```{figure} images/scene01_img01_layers.png
:width: 100%

课程配套教学图（AI 辅助绘制，非官方原图）：版本控制层负责保存代码历史，托管平台层负责团队协作与交付。
```

这样理解之后，“Git 能不能独立使用”就很容易回答：可以。Git 可以在本地仓库中工作，也可以推送到不同托管平台；平台并不改变 Git 本身的分布式版本控制模型。

## Git 与 SVN：分布式和集中式的差别

Git 的关键特点是分布式：每个开发者通常都有完整仓库和历史，可以离线提交、创建分支，再在合适的时机合并。对多人并行开发、跨地域协作和持续交付来说，这种本地工作能力很有价值。

```{figure} images/scene02_img01_git_local_history.png
:alt: Git 分布式仓库包含本地历史和分支的示意图
:width: 100%

课程配套教学图（AI 辅助绘制，非官方原图）：Git 将提交历史、分支和合并能力带到每个开发者的本地仓库。
```

SVN 的关键特点是集中式：中央仓库是团队的权威来源，开发者围绕它检出、提交和更新。权限与审计路径通常更直观；如果团队需要路径级授权，或者仓库里有大量不易合并的文件，集中式管理仍然可能合适。

```{figure} images/scene02_img02_svn_central_repo.png
:alt: SVN 以中央仓库为唯一权威来源的集中式示意图
:width: 100%

课程配套教学图（AI 辅助绘制，非官方原图）：SVN 的工作流围绕中央仓库展开，权限和提交边界更集中。
```

因此，选择轴不是“新旧”二选一，而是看团队更重视哪种约束：需要离线提交和复杂分支协作时，优先评估 Git；需要集中审计、路径权限或既有 SVN 资产时，不要忽略 SVN 的迁移成本和管理价值。

## 四个平台：仓库相同，协作侧重点不同

GitHub 的优势在于开源生态和全球协作，Pull Request、代码评审、议题和 Actions 适合公开项目或跨地域贡献者。它更像一个面向全球开发者的协作入口。


GitLab 更强调把代码、持续集成、测试、安全和部署整合到一个 DevSecOps 平台，并支持自建。它适合希望把研发流程集中管理、同时保留部署控制权的团队。


Gitee 更贴近中国大陆语境下的代码托管、中文协作、项目管理和企业研发流程。对于国内团队，网络可达性、成员习惯、权限和组织管理往往和功能清单同样重要。

CNB，即云原生构建，是腾讯云推出的开发者平台，覆盖 Git 代码托管、代码审查、声明式流水线、云原生构建、云端开发、制品库和人工智能代码助手等能力。它适合已经在腾讯云或云原生构建链路中，希望减少平台拼接的团队。

## 怎么选：先看约束，再看平台组合

把平台放在同一张表里，重点不是给出永远不变的排名，而是让团队明确自己的约束。开源项目通常优先考虑 GitHub 或 CNB 的公开协作能力；国内团队需要比较 Gitee 与 CNB 的组织、网络和研发流程；需要完整研发流程和自建能力时，GitLab 应进入重点评估范围。

```{figure} images/scene05_img01_platform_matrix.png
:alt: GitHub、GitLab、Gitee、CNB 的协作定位和能力矩阵
:width: 100%

课程配套教学图（AI 辅助绘制，非官方原图）：平台比较矩阵把开源协作、DevSecOps、自建、国内组织和云原生构建拆成可验证维度。
```

可以用四个问题快速缩小范围：项目是否面向全球开源协作？团队是否需要自建和安全流水线？主要成员和访问环境是否在中国大陆？是否希望把构建、制品和云端开发统一在同一套云原生平台中？答案比“哪个平台最流行”更有用。

最终落地前，建议用同一批真实仓库、同一套权限角色和一条代表性流水线做小范围验证，再决定长期迁移方向。

## CODING DevOps 下线后：迁移不是只搬代码

腾讯云公告给出了 CODING DevOps 的服务退出安排。对于已经使用 CODING 的团队，重点不是立刻把远端地址替换掉，而是先盘点哪些资产真的需要迁移、哪些能力需要重建。代码只是其中一部分。

```{figure} images/scene06_img01_inventory.png

:width: 100%

课程配套教学图（AI 辅助绘制，非官方原图）：迁移清单覆盖代码、分支标签、制品、流水线、凭据、权限和项目协同数据。
```

盘点后，要把旧系统里的对象映射到新平台：仓库和分支如何对应，审查规则如何重建，流水线变量和密钥如何安全迁移，制品库是否需要重新发布，成员和权限是否一一复核。


最安全的顺序是：先导出与备份，再迁移一个低风险项目；随后验证提交历史、分支标签、拉取请求、权限、流水线、制品和回滚路径；最后才安排批量切换。

## 给第一次选型的决策路径

如果你还没有明确答案，可以沿着下面的路径走：全球开源协作优先看 GitHub；需要完整 DevSecOps 和自建能力优先看 GitLab；国内团队重点比较 Gitee 和 CNB；已经在腾讯云云原生构建链路中，则优先验证 CNB。若仍在使用 CODING DevOps，先做资产盘点和小项目迁移，不要跳过回滚演练。

## 小结

Git 与 SVN 决定代码如何管理，代码托管平台决定团队如何协作和交付。Git 适合分布式、离线和分支协作；SVN 适合集中审计、路径权限和既有集中式资产。GitHub、GitLab、Gitee、CNB 的差异主要落在生态、整合、自建、地域协作和云原生构建上。

CODING DevOps 迁移时，先盘点代码、制品、流水线、权限和协作数据，再用低风险项目验证新平台。CNB 是腾讯云推荐的后续方向，但任何迁移都应以逐项验证结果为准。
